1. Core Concept (Elevator Pitch)

One-sentence definition: Calling .parallel() on a stream is a request, not a guarantee — it hands the pipeline to the shared ForkJoinPool.commonPool() (the exact framework from the previous section), which only yields a real speedup when the source can be split evenly and the per-element work is large enough to outweigh splitting/coordination overhead.

Analogy: It's like changing a form from "one clerk handles the whole line" to "any free clerk can take the next customer" — the office runs faster only if the queue is long enough and each customer takes real time; for a 3-person queue, fetching extra clerks costs more than it saves.

JVM view: .parallel() doesn't spawn new threads itself — it flags the pipeline so the terminal operation's execution engine spliterates the source and submits sub-tasks to the common ForkJoinPool, the same pool and work-stealing mechanism covered in the Fork-Join section, just invoked implicitly instead of via explicit RecursiveTasks.

2. Course Content (The "What")

Prime-counting (IntStream.range(2, N).filter(isPrime).count()): sequential ~16s vs. parallel ~2s for ~21M candidates — an ~8x speedup. count() after filter is a fully parallelizable reduction (no ordering dependency), so .parallel() before .filter() works cleanly:

long primeCount = IntStream.range(2, Integer.MAX_VALUE / 100)
    .parallel()
    .filter(MathUtils::isPrime)
    .count();

Parallel file-writing (100,000 Person objects, one file each): sequential ~7s vs. parallel ~0.68s — ~10x. Same one-line change:

people.stream().forEach(ParallelSaveOperation::save);          // sequential
people.parallelStream().forEach(ParallelSaveOperation::save);  // parallel

Called out explicitly: I/O-bound work is a strong parallelization candidate — each save() blocks on disk I/O, so overlapping many blocked calls across threads helps more than pure-CPU prime counting does per element, even though both showed strong speedups here.

Summing via LongStream.reduce:

long sum = LongStream.rangeClosed(1, n).reduce(0, Long::sum);              // sequential
long parallelSum = LongStream.rangeClosed(1, n).parallel().reduce(0, Long::sum); // parallel

At 1–2 billion elements, parallel wins ~4–5x — directly recalling the hand-rolled parallel-sum lecture from the very first parallelization section, now expressed in one line.

Explicit warning from the transcript: .parallel() is not a guarantee — some pipelines (e.g., ones using findFirst() instead of findAny()) are inherently order-dependent/sequential and won't benefit no matter how many cores are available, foreshadowing (not yet formally covered) the distinction between findFirst/findAny.

3. Practical Notes

  • Always benchmark, don't assume — exactly the same lesson as the manual-threading and Fork-Join sections: small N, order-dependent operations, or non-splittable sources (e.g., LinkedList, which splits poorly compared to an array-backed ArrayList/IntStream.range) can make .parallel() a pessimization.
  • I/O-bound parallelStream() work should not share the common pool with other CPU-bound parallel-stream code in the same application — the identical common-pool-starvation risk flagged in the Fork-Join notes applies here, just now hidden behind the one-word .parallel() call instead of explicit task code.
  • Testing: cross-check sequential vs. parallel results on identical input (as the course itself does for both the prime count and the sum), and avoid any shared mutable state inside the lambda passed to forEach/filter/map — the same warning as before, now doubly relevant since .parallel() can be added to any existing pipeline with no visible code signal that concurrency has been introduced.

4. Tradeoffs (The "Why")

Workload Speedup shown Why
Prime counting (CPU-bound, 21M ints) ~8x Pure computation per element, easily split, no I/O wait
File writing (I/O-bound, 100K files) ~10x Threads overlap while waiting on disk, not just CPU
Sum reduction (CPU-bound, 1–2B longs) ~4–5x Simple per-element op, overhead amortizes only at huge N

Same pitfalls as Fork-Join carry over unchanged: order-dependent terminal ops don't parallelize; blocking calls inside a parallel-stream lambda can starve the shared common pool; small inputs make .parallel() a net loss due to splitting/scheduling overhead.

5. Interview Q&A

Basic: Does calling .parallel() guarantee parallel execution? No — it's a hint; whether real parallel execution happens (and helps) depends on the source's splittability and whether the terminal operation is order-independent.

Intermediate: Why did the file-saving example show a bigger relative speedup than pure prime-counting? Because file I/O involves blocking wait time per element that multiple threads can overlap, not just CPU work — parallelism hides I/O latency in addition to spreading computation.

Advanced: Why might findFirst() prevent effective parallelization while findAny() wouldn't? findFirst() must respect encounter order — the implementation still has to determine which qualifying element truly comes first across all parallel chunks, which reintroduces a sequential dependency; findAny() has no such constraint and can return as soon as any thread finds a match, making it far more parallel-friendly.

6. Mastery Checklist

  • I can add .parallel()/parallelStream() to an existing pipeline and explain that it's a request, not a guarantee, backed by the common ForkJoinPool.
  • I can identify CPU-bound vs. I/O-bound workloads as both being good parallelization candidates, for different underlying reasons.
  • I know to benchmark rather than assume, and to watch for order-dependent operations (findFirst) or common-pool starvation from mixed I/O/CPU parallel-stream use.
